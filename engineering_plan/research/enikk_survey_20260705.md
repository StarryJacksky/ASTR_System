## 一、它的架构（与我们的逐条对照）

### 1. LLM 是带工具的 ReAct agent，不是固定状态机 ★核心差异
- **它**：`analyze()/click()/wait_for()/read_image()` 都是工具，LLM 在 Hermes 工具循环里自主决定
  何时感知、何时行动、何时验证、何时升级到视觉。系统提示明写节奏："analyze → think → act → analyze"。
- **我们**：CuEngine 固定状态机，每步必截图→必规划→必执行，模型没有"多看一眼再动"的自由。
- **最要害的推论：决策模型不需要视觉能力。** `analyze()` 返回结构化元素清单
  （RapidOCR 文本 + YOLO 图标 + **预计算 center 坐标**，[0,1000] 窗口归一化），LLM 从清单挑坐标，
  grounding 负担为零；`read_image()`（VLM 看图）只是可选升级路径——"多数操作从不需要昂贵的视觉模型"
  （它的"progressive perception"）。→ **我们的本地 qwen3-8b（纯文本）就能当规划器**，
  UI-TARS 不必扛全场。这等于给我们的 two_stage 正名并指出改进方向，而不是推倒重来。

### 2. 一切以 hwnd 为界：窗口即地盘 ★结构性优于我们的围栏
- 截图 = **窗口客户区**（mss 按窗口矩形抓，不是全屏）→ 图小（快）、文字清晰（OCR/模型都受益）、
  桌面其他内容物理不可见（隐私+纪律双赢）。
- 坐标 = [0,1000] 相对窗口客户区归一化 → 与屏幕分辨率解耦。
- **每个动作**先 `force_foreground(hwnd)`（AttachThreadInput 三连招）→ 焦点问题在动作级解决。
- 我们的 title_fence 是事后围堵；hwnd-scoped 是事前结构——她的世界就是那扇窗。
  注意坑：右键菜单/对话框是独立 hwnd，Explorer 场景要处理"窗口家族"（owner 链），游戏场景没这问题。

### 3. wait_for(text)：语义等待
OCR 轮询直到目标文字出现（模糊匹配阈值 0.7，默认 5s 间隔 90s 超时），替代盲等+反复截图。
比我们的固定 0.8s 稳定窗高明——"UI 到位"由内容定义，不由时钟定义。

### 4. 技能 = SKILL.md 知识包 ★与 99#24 实时学习直接同构
- 格式：YAML frontmatter（name/description 触发词/tags/platforms）+ Markdown 正文
  （UI 参考：大厅 21 个按钮的位置与语义全部人肉标注；工作流；注意事项）。
- 系统提示第一条铁律："**先查技能再动手，不要猜**"。
- README 声称任务后自动复盘提取技能入库（self-improving；提取逻辑在 Hermes 侧未开源细节）。
- **最深的洞见：enikk 能打游戏不是因为模型强，而是知识外置**——技能书把路线图全喂了。
  我们 8 轮里程碑失败的对偶解释：我们一直要求 7B 每轮从零重新发明"资源管理器怎么用"。
  若有一份《资源管理器技能》（建文件夹=点功能区新建文件夹按钮(约182,58)→输入名→enter；
  移动=剪切粘贴流……），7B 只需照方抓药。**可教性 > 模型能力**，这正是麦麦式"越待越会"的效应器版。

### 5. 鼠标拟人化（Jacksky 观察到的"Codex 丝滑感"的实现）
三次贝塞尔曲线路径 + 每段 ±1.5px 抖动 + 变速（两端慢中间快）+ **30% 概率过冲 4px 再回正**。
我们刚加的 easeOutQuad 是简化版；它的版本可直接抄（`input.py:_human_move_to`，~40 行）。

### 6. 本体感：analyze() 回传当前鼠标位置（归一化）+ SoM 标注图上画红十字
模型知道"我的手现在在哪"。我们的规划器完全没有这个信息。

### 7. 其他可取件
- `steer_session()`：任务跑一半主人插话转向（我们礼让的正向版：主人不只能打断还能指挥）。
- `close_window()` 三级降级：WM_CLOSE→terminate→kill。
- SoM 标注图（彩色框+标签+坐标）既给 VLM 升级路径用，也是人肉调试利器。
- IM 遥控（QQ/NapCat）+ Web 控制台 + cron 定时任务——与我们平台栈同构，验证了方向。

## 二、诚实的局限（不必神化）
- 26 星、个人项目、游戏场景特化：单窗口、UI 布局恒定、无文件系统风险、失败可重来。
- **没有护栏概念**：无白名单、无审批档、无审计链、无急停——安全面我们远超它（我们的护栏经过
  红队 22/22 与 8 轮真机事故淬炼，这是不能拿去换丝滑的部分）。
- "自动技能提取"的实现在 Hermes 侧，本仓只见 sync；实际内置技能是人手写的。
- 游戏 UI 元素大且稀疏，OCR/YOLO 命中率天然高；生产力软件（密集小字+多级菜单）难度高一档。

## 三、给 ASTR 的改造方案（P2.5 二期卡，按优先级）
1. **hwnd-scoped CU 模式**（结构解，替代大部分围栏职责）：capture/click/type 全部以任务窗口
   客户区为界+窗口归一化坐标；每动作前 force_foreground。围栏保留为第二道防线。
2. **清单驱动规划（two_stage 复活升级）**：窗口小图 → OmniParser（YOLO+OCR；Florence caption
   只对无字图标做，窗口图上量级会掉一个数量级）→ 元素清单带 center → **qwen3-8b 文本规划**
   （本地、快、截图不出网）→ 点 center。UI-TARS 降级为"清单找不到目标"时的视觉兜底。
   预期：单步 <5s（vs UI-TARS 1568px 的 23s），且规划质量吃 qwen3-8b 的语言能力而非 7B VLM 的短板。
3. **效应器技能库**：`soul_package/justin/skills/effector/*.md`（SKILL.md 同款格式），
   系统提示"先查技能，不要猜"；先人手写《资源管理器》一份，用它重跑里程碑验证"可教性>模型"假设；
   任务后复盘提取进 P4-W1（与 99#24 表达学习共用复盘管线）。
4. **wait_for(text) 语义等待** 入 CuEngine 动作面。
5. **鼠标拟人化升级**：抄 `_human_move_to`（贝塞尔+抖动+过冲）。
6. **mouse_position 本体感**：截图时一并回传鼠标归一化位置给规划器。

## 四、裁定
Enikk 单点技术皆平凡，组合方向正确且与我们互补：**它有肉身智慧（窗口作用域、渐进感知、知识外置）
没有安全骨架；我们有安全骨架，肉身太僵**。取其 1-3 条即可让本地档翻身——尤其"决策不需要视觉"
一条，直接解开"7B VLM 编排弱"的死结：让 qwen3-8b 想，让 OmniParser 看，让 UI-TARS 兜底。
